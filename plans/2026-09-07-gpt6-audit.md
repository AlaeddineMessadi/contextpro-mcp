# ContextPro: reliability and agent efficiency audit

Audited 2026-09-07 against commit `02e1398`. This is an assessment and proposed execution order, not an implementation. Source code was not changed.

ContextPro already has the useful foundation: structural indexing, lexical fallback, exact-reference evidence, bounded task packets, worktree routing, restore points, and regression tests. The next release should strengthen the guarantees behind these capabilities before expanding the tool catalog.

## Verification and scope

- TypeScript: `./node_modules/.bin/tsc --noEmit` passed; the test prebuild also passed.
- Full main suite: **545/545 tests passed** in 22.23 seconds with `CONTEXTPLUS_NATIVE_AUTO_REPAIR=false node --test test/main/*.test.mjs`, after rebuilding current source. Initial tests were disrupted by missing/mismatched native SQLite bindings; these environment failures were not counted as product defects. The final run used the compatible Node 24 runtime with native auto-repair disabled to avoid rebuilding shared dependencies for competing Node ABIs. An intermediate run set both old and new repair variables and passed 544/545; the remaining test assumed the new variable was unset. The final legacy-only setting preserved that test's intended environment.
- Controlled temporary fixtures reproduced the edit, reconciliation, worktree, import, memory-cache, search-filter, and output-budget findings below. Fixtures were removed. The symlink finding was confirmed at the shared guard and traced to file-write sinks.
- In-memory MCP client/server negotiation measured the actual `tools/list` surface: **core: 37 tools, 47,996 JSON bytes; full: 59 tools, 73,144 bytes**. Byte/4 estimates are roughly 12,000 and 18,300 tokens; these are proxies, not tokenizer measurements or guaranteed per-request costs. Clients that defer tool loading incur different costs. Only `graph_query` advertises an output schema.
- Runtime dependency check: `npm audit --omit=dev --json` reported zero advisories.
- Scope: core MCP engine, retrieval, task packs, indexing, graph freshness, source mutations, project boundaries, tool registration, tests, existing design and roadmap documents. Dashboard/landing applications, every supported grammar, real hosted embedding providers, and large-repository end-to-end performance were not exhaustively audited.

## Reproduction evidence and fix boundaries

### 1. Filesystem containment

A symlink inside a temporary project pointing into a sibling directory passed `resolveProjectPath`, although its real target was outside the project. The shared guard uses `resolve`/`relative`, which check spelling rather than filesystem identity. Checkpoint and restore subsequently call `writeFile` on the accepted path.

Resolve the canonical root and existing target or nearest existing parent for new files. Define an explicit policy for source symlinks, cover symlinked directories as well as individual files, and account for link replacement between validation and mutation. Do not describe a lexical-only check as a security boundary.

### 2. Concurrent writes

Two simultaneous `replaceSymbolBody` calls changed distinct functions in one fixture. Both returned success; one replacement vanished. The manifest mutex serializes backup metadata, not the complete source read/modify/write operation.

Use one mutation path with per-file coordination across MCP processes, expected source hashes, conflict reporting, and atomic publication. External editor writes must also be detected. Snapshotting alone is insufficient. Apply the same semantics to replacement, insertion, checkpoint, rename, and restore.

### 3. Symbol edit precision

A file containing two exported functions on one line lost the second function when the first was replaced. Whole-line splicing cannot distinguish the two spans.

Carry exact source offsets through extraction and splice the selected declaration only. Immediately reject edits whose current line-only spans include unrelated code; that is a small protective step before the broader offset migration. Cover Unicode, declaration wrappers, inline class members, and neighboring declarations. Syntax checks should remain, but cannot prove that unrelated code was preserved.

### 4–5. Reconciliation correctness

**Deletion:** after caching a graph and deleting a file, reconciliation reported one removal. A subsequent freshness check reported `staleCount=0`, yet the cached graph still included the deleted file; generation remained unchanged.

**Backlog:** edit three existing indexed files and reconcile with `maxFiles=1`. Sweep one returned `refreshed=1, drifted=3, pending=2`. Sweep two returned all zeros. The database still contained the old symbols for two files. The current cap regression uses new files, which do not enter this faulty stat-cache branch.

Route deletion through the same coordinated generation/invalidation mechanism as other structural changes. Cache a file as reconciled only when its stored content matches, or retain explicit pending state across sweeps. Verify failed refresh retries as well as capped batches. Query-time refresh can repair some backlog cases later; it does not make the background guarantee correct.

### 6. Worktree initialization

A seeded worktree copied `index_status=indexing` and the live base owner's PID. Setting the base database back to idle left the worktree indexing. A bounded wait in the worktree timed out. The current recovery only clears known-dead owner PIDs or expired legacy locks.

Use a consistent SQLite snapshot, remove transient indexing ownership from the destination, and publish it without overwriting a concurrently initialized worktree. The current existence check followed by unrestricted `copyFile` also leaves a race; include simultaneous first-request coverage in this fix.

### 7. Incoming import resolution

Index `a.ts` while its imported module is absent, then add that module as `b.ts` and quick-refresh. `b.ts` became indexed, but the old import retained `target_file_id=null`, and its reverse-importer list stayed empty.

Re-resolve relevant incoming and unresolved imports when the file set changes, including deletion/recreation and extension/index precedence. Do not rebuild every importer indiscriminately on every content edit.

### 8. Response budgets

With a 7,819-character task and `maxTokens=512`, a public task-pack fixture returned 17,044 characters, roughly 4,261 tokens under its own character/4 convention. The pruner can stop with oversized mandatory fields; the text renderer repeats task text outside the payload estimate.

Budget the final rendered response, reserve metadata overhead, and bound free-text fields. Preserve useful file pointers with artifact expansion when details do not fit. If a minimum response cannot fit, report that explicitly. Add whole-response tests for text and JSON, long tasks/reasons/memory, small budgets, and Unicode. Document whether the guarantee is measured tokenizer tokens or an approximate byte budget.

### 9. Memory-aware artifact freshness

A cached pack contained one memory. After recording another matching memory, direct memory retrieval found two, but `ensureFreshIndex` followed by the same task pack returned the old single-memory cache hit. Code generation stayed at one.

Track memory revision separately and include it in relevant artifact freshness. Review other mutable inputs such as Git state at the same time, without assuming that every artifact depends on every revision. Do not force a source reindex merely to refresh memory.

### 10. Search contracts

`semanticCodeSearchResults` with `minSemanticScore=0.8` returned a lexical result with `semanticScore=0` and `score=100`. FTS injection occurs after initial filtering. A rank score is not calibrated confidence.

Apply all explicit hard constraints after candidate generation and boosts. Preserve lexical fallback when callers have not requested a semantic constraint. Test unavailable providers and exact-symbol boosts as well as plain FTS injection.

### 11. Rename validation

A rename to a language keyword returned success after producing invalid TypeScript. Check new-name validity for the actual language, stage all candidate contents, and validate before any file is changed. Surface partial failures explicitly. The separately documented limitation that rename is textual and does not resolve scopes is not a new finding.

## Product direction: four focused improvements

### A. Measure completed tasks, not hypothetical whole-file reads

The existing roadmap already puts a retrieval benchmark first (`docs/roadmaps/contextplus-agentic-code-intelligence-roadmap.md`). Follow through with a fixed corpus of realistic coding tasks: locate an implementation, explain a dependency, fix a multi-file bug, choose tests, and recover from a stale index. Include TypeScript, Python, a monorepo, worktrees, and a project with no embedding provider.

Compare ContextPro against an agent using ordinary search/read tools. Measure task correctness, retrieval recall, follow-up reads, total input/output tokens including tool descriptions, cold/warm latency, provider requests, and concurrent throughput. Keep cheap deterministic retrieval checks separate from costlier live-agent evaluations. Establish baselines before inventing target percentages. Effort: M for an initial harness, L for representative live-agent coverage.

The current efficiency estimator counts represented files' entire byte sizes and accumulates savings on repeated calls (`src/core/efficiency.ts:90`, `src/core/efficiency.ts:118`). It is explicitly labeled an estimate and is useful as a compactness proxy, but it cannot establish the README's typical 75% agent-token reduction or actual billing savings. Do not use it as the optimization objective.

### B. Offer a genuinely small agent profile

Keep backward-compatible `full` and `core`, but add a workflow profile around 8–12 frequently useful operations. Prototype a set such as task pack, search, skeleton, explain, impact, validation, memory, and status; let benchmark results decide the exact set. Expose optional graph, editing, and administration capabilities separately. Avoid replacing all schemas with an untyped universal dispatcher.

Current evidence is concrete: 37 core tools and nearly 48 KB of definitions (`src/core/tool-profile.ts:13`). Also measure description/schema bytes in CI so additions have visible costs. Trade-off: smaller menus may require deliberate profile selection for specialized tasks. Effort: S/M.

### C. Return only new context within a session

Extend existing artifacts with content IDs, source revisions, a session's previously delivered context IDs, and an explicit continuation cursor. A follow-up packet could return changed spans and newly relevant callers instead of repeating prior material. The full context must remain retrievable for a new agent or compacted session; never silently assume it is remembered.

Task-pack artifact reuse already supplies the foundation (`src/tools/agentic-context.ts:437`). Cache invalidation and hard response budgets should land first. Trade-off: additional session state and recovery semantics. Effort: M/L.

### D. Make lexical discovery fast and predictably offline

A warm file-search `keyword_only` fixture still invoked the embedding provider once. The file-search layer sets weights but still calls `SearchIndex.search`, which embeds the query (`src/core/embeddings.ts:646`); the identifier path independently embeds it too (`src/tools/semantic-identifiers.ts:494`). Make zero-provider lexical execution explicit and test provider-call counts. Share query embeddings across hybrid branches when embeddings are needed; avoid calculating caller details that the task packet immediately discards.

Only then benchmark bounded graph expansion from the strongest symbol anchors into definitions, callers, and relevant tests. The existing graph makes this possible, but expansion should ship only when it improves task results per token. Trade-off: skipping semantic work changes available evidence; report the selected retrieval mode accurately. Effort: M.

## Suggested execution order

1. Land regression fixtures and fixes for workspace containment and edit data loss. Begin with rejection of unsafe ambiguous edits, then implement the shared mutation mechanism and exact spans.
2. Fix reconciliation generation/backlog handling, then worktree initialization and incoming import repair. These are prerequisites for trusting graph-based feature work.
3. Enforce response budgets, final search filters, and memory-aware cache invalidation.
4. Establish the retrieval/agent benchmark baseline and add the smaller workflow profile.
5. Prototype context deltas and bounded graph expansion; retain only demonstrated improvements.

Detailed executor plans should be selected from this list rather than creating an implementation plan for every finding at once. Recommended first batch: safe edits, reconciliation correctness, response budgets, and the benchmark harness.

## Considered and rejected or deferred

- Ordinary source edits bypassing task-pack cache freshness were considered, then rejected as a public MCP finding: the registration wrapper runs `ensureFreshIndex` first. Memory-only updates remain a separate reproduced bug.
- Heuristic call graphs outside TS/JS and imported SCIP, local project-validator execution, and explicit root overrides are documented tradeoffs, not bugs by themselves.
- Do not rewrite the storage engine, add another dashboard/TUI, or add more provider integrations before measurement demonstrates a need. The current SQLite and graph foundation is adequate for this next phase.
- Do not treat raw tool-schema bytes as billed tokens, or repeated whole-file avoidance estimates as measured agent savings.
- `STATUS.md` is stale relative to current package/tool/worktree behavior; reconcile release documentation when the next fixes ship, rather than making document cleanup the main project.
