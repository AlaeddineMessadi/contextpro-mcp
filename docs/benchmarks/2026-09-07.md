# ContextPro measured benchmark — 7 September 2026

ContextPro reduces retrieval output in text mode and improves required-file coverage on this small repository sample. It does **not** demonstrate lower total agent tokens, actual money savings, or faster completed coding tasks. Its local retrieval operations were slower than the compact Git/ripgrep baseline. JSON and tool-catalog overhead can erase the output savings.

## What was actually measured

- Source: frozen archive of `36d161b`, 265 scanned files / 235 indexed source files. No production source edits were made for this evaluation.
- Runtime: Node v26.0.0, launched with the ContextPro entry from Codex's local configuration; Ollama, `bge-m3:latest`, lazy embedding tracker. The chat model was configured as `kimi-k2.6:cloud`; the measured retrieval workflows did not intentionally invoke chat generation. Provider billing/energy costs were not collected.
- Six hand-authored discovery tasks: native repair, safe source writes, failed reindex, token accounting, worktree snapshots, and grammar loading.
- Four strategies × six tasks × three serial repeats = **72 retrieval runs**. Execution order rotated across tasks/repeats. All 72 completed without errors.
- Baseline: tracked text discovery with Git, ripgrep matches ranked by distinct manually supplied keywords and then matching-line counts, then up to three matching windows with two context lines per top-five file. No expected file paths enter the ranking algorithm. This is a scripted compact baseline; the time/reasoning to select those keywords is not measured.
- ContextPro: file search, top five, crux excerpts; keyword-only JSON, balanced JSON, balanced text. This evaluates explicit file mode, not every default hybrid/task-pack workflow.
- Quality: manually specified implementation-file coverage in the top five. Average recall weights each task equally. “Complete” means every expected file was returned, **not** that an agent solved the task or that snippets supplied all necessary facts. Repeats do not increase the sample size for quality conclusions.
- Tokens: captured text encoded with `o200k_base` and `cl100k_base` using tiktoken. Counts are exact for these reference encodings. Neither is asserted to be the GPT-6/Claude billing tokenizer. Main tables use `o200k_base`; the second encoding gives similar results.
- Timing: measured wall time per tool operation. These are warm-provider/OS measurements; startup and incremental index reconciliation are separate. Existing embeddings were seeded via SQLite's online backup. Their original construction cost is not included. No independent operations were overlapped during the measured retrieval runs.

The pilot indexed the benchmark's own task descriptions. It was rejected. The final corpus excludes the new harness and reports; both strategies operate against the frozen checkout. Existing repository docs, fixtures, and earlier audit plans remain in the corpus. The baseline searches tracked text including docs/configuration, excluding lockfiles; ContextPro applies its own scanner rules. This is not an identical document-universe comparison or a blind, held-out evaluation.

## Results

Response tokens below count one pass through the six tasks, not repeated consumption or total agent input. Catalogs and requests are separate.

| Strategy | Response tokens | Difference vs rg | Median operation | Mean required-file recall | Complete file sets |
| --- | ---: | ---: | ---: | ---: | ---: |
| Compact Git/rg | 10,003 | — | 32.5 ms | 80.6% | 3/6 |
| ContextPro keyword-only, JSON | 13,364 | 33.6% more | 185.4 ms | 72.2% | 2/6 |
| ContextPro balanced, JSON | 11,731 | 17.3% more | 273.4 ms | 86.1% | 4/6 |
| ContextPro balanced, text | 5,917 | **40.8% fewer** | 219.6 ms | **86.1%** | **4/6** |

Balanced text avoided **4,086 response tokens** across the six tasks. It was about **6.8× slower per operation at the median**. The first six text calls totaled 3.731 seconds versus 0.201 seconds for the baseline: **3.530 seconds more retrieval time**, including two slow first-pass outliers. A shorter model prompt could offset some latency later, but that was not measured.

On the two tasks where both strategies returned the entire required file set (worktree snapshots and grammar loading), balanced text used 2,047 versus 3,144 response tokens: **1,097 fewer / 34.9%**. These are still file-discovery results, not completed coding tasks.

The safe-write response is smaller partly because it misses `src/core/path-guard.ts`. That is a quality loss, not a successful optimization. Balanced retrieval repairs that particular miss.

## Catalogs, structural output, and deltas

The advertised catalog is **16,944 reference tokens for 59 tools**, versus **3,997 for the 12-tool workflow profile**: 12,947 fewer / 76.4%. This is serialized catalog size, not measured client prompt usage. Clients may discover tools lazily or cache schemas differently.

As an explicit scenario, charging one entire full catalog against this six-task sample exceeds the 4,086 response-token saving by **12,858 tokens**. One workflow catalog leaves only **89 tokens** before request and client overhead. This comparison does not subtract the baseline's tool schemas and is not a billing calculation. It shows why catalog behavior must be measured in a real agent trial.

Three skeletons returned **1,345 tokens** versus **5,181** for whole-file bodies (74.0% less). An export-line grep used only 248 tokens, but omitted internal functions, multiline types, and dependencies. Skeletons also omit useful information: `getNativeRuntime` ends at `): {` without its object return fields, interface members are absent, and `estimateToolEfficiency` is truncated with an ellipsis. Structural compression therefore cannot be equated with complete API understanding.

An unchanged task-packet delta used **722 tokens** versus **1,018** for the full packet, a 29.1% response reduction. Including serialized request arguments reduced this example's advantage to 280 tokens. Returning an unchanged delta still spends hundreds of tokens on repeated metadata. The packet also inherited keyword-only ranking misses, so this is a compression observation only.

The built-in session report stated **~27,851 tokens avoided versus full-file reads**, using its bytes/4 estimator. That session includes all repeated MCP calls and a different baseline. It is not the measured 4,086-token comparison and must not be presented as actual saved tokens. Actual agent token savings, dollars saved, and completed-task time savings remain **unknown**.

## Reliability

All 72 retrieval runs and the auxiliary structural/packet calls completed. A separate forced structural reindex processed all 235 source files, extracted 7,387 symbols and resolved 1,369 imports in **6.102 seconds** server time (6.349 seconds tool round trip). A subsequent status call succeeded and reported a fresh index. This did not reproduce the earlier disconnect. It does not exercise eager embedding generation, sustained concurrency, or every client runtime.

The existing five-task synthetic benchmark also ran; both ordinary rg and ContextPro search achieved full expected-file recall. Its tiny fixtures and bytes/4 metric are regression checks, not evidence of real agent savings.

## Improvements supported by the results

1. **Reduce catalog overhead.** Promote the existing workflow profile in agent setup and provide an on-demand way to reach expert tools. Measure the client's actual schema injection before claiming a net saving. Keep exact-reference/edit tools available when needed; blindly disabling them would trade away safety.
2. **Use concise text for agents and add compact structured output.** Balanced text was 49.6% smaller than JSON with the same ranked files. JSON repeats freshness, paths, artifact metadata and symbol information. A compact JSON mode should preserve freshness warnings and exact locations while removing duplication. Gate it on unchanged rankings and materially fewer tokenizer-counted tokens.
3. **Fix retrieval completeness before tuning for size.** Add the safe-write and accounting misses as regression cases, then evaluate on new repositories. Combine lexical candidates with semantic retrieval and bounded import expansion so `path-guard.ts` and `runtime-session.ts` can be discovered. `splitCamelCase` in `src/core/embeddings.ts` uses broad term coverage without stopword/IDF weighting; that is a plausible contributor to generic natural-language matches, not a demonstrated single cause. Compare BM25/IDF and source-vs-document ranking as controlled experiments.
4. **Preserve API contracts in skeletons.** Include interface members and complete multiline parameter/return types; add an exported-only view for agents that just need the public API. Verify the rendered signatures against compiler-derived declarations. Do not advertise a token win by discarding fields required to call the function correctly.
5. **Profile retrieval overhead before changing freshness rules.** Repeated searches still took roughly 0.2–0.3 seconds. Instrument freshness scans, embedding requests, ranking, artifact writes and efficiency accounting separately. Cache immutable intermediate work by index generation; keep reliable invalidation. The current measurements do not identify a dominant component.
6. **Make unchanged deltas genuinely small.** Return context ID, generation and an explicit unchanged marker, keeping full recovery available. Test that applying a delta preserves the complete packet and measure request plus response size.
7. **Add an actual paired-agent benchmark.** Fresh isolated sessions, same model and task budget, counterbalanced order, identical acceptance tests, multiple held-out repositories, and both successes and failures retained. Record provider input/output/reasoning/cache usage, schema overhead, wall time, tool errors, patch correctness and explicit price provenance. Extend `benchmark-agent-runs.schema.json` for timing and cache usage. This is required before claiming real money or total-token savings.
8. **Harden concurrent grammar initialization.** Inspection of `src/core/tree-sitter.ts:116` shows resolved-value caches without an in-flight promise for parser initialization or grammar loading. Concurrent cold parses can repeat initialization/loading. Deduplicate those promises and test concurrent first-use behavior. The benchmark did not prove this caused the previous V8 crash.

Agent guidance should be “ContextPro first for unfamiliar discovery; targeted tools for exact work; fall back when coverage is weak.” An unconditional requirement to use every MCP step can consume more tokens than it saves. Completion reports should separate measured usage, reference-tokenizer counts, full-file compression estimates, and hypothetical cost scenarios.

## Artifacts and reproduction

- `2026-09-07-results.json`: per-task counts, timings, named tokenizer results, methodology and limitations.
- `2026-09-07-stability.json`: forced reindex result.
- Local raw captures, catalogs, stderr, synthetic results and rejected pilot: `.contextpro/benchmark-2026-09-07/`. These source-containing captures are intentionally ignored by Git.
- Runner: `scripts/benchmark-live.mjs`; counter: `scripts/tokenize-live-benchmark.py`.

To reproduce, create a temporary frozen archive of the source revision, excluding the new benchmark harness/reports so queries cannot match themselves. Initialize Git in that snapshot and commit its files. Seed its index using the production `seedWorktreeFromBase(snapshotRoot, originalRoot)` helper, with the same configured embedding model. Then, from the original repository:

```sh
/opt/homebrew/bin/node scripts/benchmark-live.mjs /absolute/frozen/checkout .contextpro/benchmark-repeat
uv run --with tiktoken python scripts/tokenize-live-benchmark.py .contextpro/benchmark-repeat
```

The runner reads only the ContextPro configuration entry from local Codex configuration. It runs an incremental structural reconciliation before timing, records startup separately, saves raw tool text, and opens a second MCP connection to measure the workflow catalog. It rejects a target containing its own script. Provider caches and OS caches are not reset; results should not be labelled cold-start measurements. Temporary snapshot source and seeded indexes contain local project data and can be deleted after preserving the desired measurements.
